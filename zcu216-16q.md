# The 16-qubit ZCU216 build (430 MHz)

This page describes the 16-qubit configuration of [`PulseTableSoc`](docs/soc/PulseTableSoc.md) on the ZCU216
and the workflow that turns it into a bitstream. It covers what differs from the 14-qubit build of
record, why the design runs `dspClk` at 430 MHz rather than 500 MHz, and how the board's clock chips
are set for it.

| | |
|---|---|
| Config | [`software/configs/zcu216-16q-430.json`](software/configs/zcu216-16q-430.json) |
| Cores / qubits | 16, one RISC-V core per qubit |
| `dspClk` | 430 MHz (2.326 ns) |
| DAC / ADC rate | 6.88 GS/s (16 samples per cycle) / 1.72 GS/s (4 samples per cycle) |
| Timing | met first pass: `dspClk` WNS +0.016 ns, 0 failing endpoints; WHS +0.006 ns |
| Utilisation | LUT 52 %, FF 53 %, DSP 76 %, BRAM 9 %, URAM 20 % |
| Build time | about 3 hours (2 h 42 min measured, Vivado 2026.1) |
| Hardware status | bitstream built; **not yet run on the board** (the clock-chip settings are derived, see [Clocking](#clocking)) |

## The design

### Cores and channels

The config uses the legacy SocParams form (`qubit_num: 16`), so every core gets the three standard
channels from [`SocSpec`](docs/soc/SocSpec.md): `gate` (a pulse drive), `ro` (the readout drive, traced) and
`demod` (the readout demodulator). The converter maps put each qubit's gate on its own DAC and share
the readout path per group of eight qubits:

| Physical converter | Carries |
|---|---|
| DAC 0–13 | the gate channel of qubit 0–13, one each |
| DAC 14 | qubit 14's gate + the readout drives of qubits 0–7 (9 channels) |
| DAC 15 | qubit 15's gate + the readout drives of qubits 8–15 (9 channels) |
| ADC 0 | the demodulators of qubits 0–7 |
| ADC 4 | the demodulators of qubits 8–15 |

Readout is frequency-multiplexed: each qubit's readout channel plays its own tone, the channels that
share a DAC are summed by an [`AdderTree`](docs/dsp/AdderTree.md) (no saturation — the sum wraps, so
software keeps the combined amplitude within full scale), and each demodulator picks its own tone out
of the shared ADC stream. Qubit drive and readout frequencies must be far enough apart for DAC 14/15's
gate drive to coexist with the readout tones.

### Floorplan

The 14-qubit floorplan pins three cores per X0 clock-region row over Y3–Y7, which holds 15 cores at
most. The 16-qubit build uses the **span** floorplan instead (`RISCQ_SPAN=5` in
[`pblocks-bd.tcl`](vivado-scripts/riscvsoc-bd/pblocks-bd.tcl)):

- the SLICE rows of X0Y3–X0Y7 (Y180–Y479) are cut into 16 equal bands of 18–19 rows, one per core;
  a band may straddle a clock-region boundary and is clipped to the X0 column on both sides;
- the datapath is confined to `CLOCKREGION_X1Y0:X5Y7` as in the 14-qubit build.

The span form was chosen over 4 cores per row by measurement at 500 MHz: both missed by about
0.21 ns, but the span build halved the failing endpoints (8,657 vs 18,438) and the total negative
slack (−544 vs −1,051 ns).

### RTL changes for 16 qubits

Two paths were the worst in the first 16-qubit builds and are fixed in the RTL:

- **Channel time replica** ([`PulseTableSoc`](docs/soc/PulseTableSoc.md),
  [`RiscqRfWithPulseTableFiber`](docs/soc/RiscqRfWithPulseTableFiber.md)). Each core's channels used to take
  their time broadcast from `coreTime_i`, which is pinned in the core's X0 band, so every channel's time
  register was a zero-logic wire across the die. A second replica, `chanTime_i`, now feeds the channels
  and floats with the datapath. It has the same latency from `syncTime`, so the channels see the
  identical time every cycle.
- **PutHub priority enable** ([`PutHub`](docs/soc/PutHub.md)). The round-robin priority register was enabled
  by the 17-way grant. It is now enabled by `valids.orR`, which is equivalent (a round-robin grant is
  non-empty iff a source is valid) and skips the arbiter.

## Clocking

### Why 430 MHz

The design does not close at 500 MHz with 16 cores (see [Timing results](#timing-results)), and the
board's clocking rules out most frequencies between 430 and 500 MHz:

1. **The DAC tile PLL.** The DACs run at 16 × `dspClk`. DAC tile 2's internal PLL makes that rate
   from a `dspClk`-rate reference only up to about 6.88 GS/s (`dspClk` ≤ 430 MHz) or from about
   7.9 GS/s (`dspClk` ≥ about 492 MHz). In between, the tile needs the full sample-rate clock on its
   reference pins.
2. **The CLK104 card.** DAC tile 2's reference pins are driven by the LMK04828, which tops out near
   3 GHz. The card's LMX2594 can make several GHz but reaches the converters only through optional
   SMP cables, and those go to tile 1, not tile 2.
3. **The LMK04828 itself.** It makes every output by dividing a VCO of 2370–2630 MHz (VCO0) or
   2920–3080 MHz (VCO1) by an integer, so nothing between about 440 and 474 MHz is reachable.

430 MHz is the highest `dspClk` that satisfies all three. Builds at 450 and 475 MHz were made and met
or nearly met timing, but their bitstreams cannot be clocked on this board; `rfdc-config.tcl` now
prints a `CRITICAL WARNING` for any such frequency.

### The clock tree at 430 MHz

| Source | Output | Feeds |
|---|---|---|
| LMK04828 VCO0 | 2580 MHz = 160 MHz (VCXO) ÷ 8 × 3 × 43 | the output dividers |
| DCLKout0/2/4/6/10/12 | 2580 ÷ 6 = 430 MHz | ADC/DAC tile reference clocks, LMX inputs |
| DCLKout8 (PL_CLK) | 430 MHz | `dspClk` pins (E10/E9) |
| SYSREF | 2580 ÷ 264 = 9.77 MHz (`dspClk` ÷ 44) | RF and PL SYSREF for multi-tile sync |
| ADC tile 2 PLL | 1.72 GS/s from the 430 MHz reference | distributed to ADC tiles 0, 1, 3 |
| DAC tile 2 PLL | 6.88 GS/s from the 430 MHz reference | distributed to DAC tiles 0, 1, 3 |

The SYSREF divider is even so that SYSREF also divides the ADC fabric clock (`dspClk` ÷ 2), as
multi-tile sync requires.

### Where the frequency is set

Everything follows `dsp_freq_hz` in the build's config; nothing else needs editing:

| Stage | File | What it does with `dsp_freq_hz` |
|---|---|---|
| Build driver | `vivado-scripts/riscvsoc-bd/build-riscvsoc-bd.sh` | reads it from the config into `RISCQ_DSP_FREQ` (override by setting that variable) |
| Clock constraints | `inc/bd-finalize.tcl` | writes a per-build copy of `constraints-zcu216.xdc` with the 2.000 ns periods replaced |
| RF Data Converter | `inc/rfdc-config.tcl` | sets sample, reference and fabric clock rates; keeps the tile-2 PLLs when their range allows |
| Board clocks | `software/riscq/board/clk104.py` | derives the LMK04828 registers for that frequency from AMD's CLK104 table |
| Driver bring-up | `software/riscq/board/pynq_driver.py` | programs the LMK for the bundle's frequency (500 MHz builds keep the established 500.25 MHz setting) |

`clk104.py` starts from AMD's own ZCU216 table (embeddedsw rfclk `xrfclk_LMK_conf.h`,
"250M_PL_125M_SYSREF_10M") and changes only the fields that differ between AMD's two shipped configs:
the VCO select, PLL2 R/P/N, the output dividers and the SYSREF divider. `tests/test_clk104.py` checks
that it reproduces both AMD configs, apart from the PL clock and SYSREF fields it sets on purpose. The
generated settings have not yet been run on hardware.

## Building the bitstream

### Prerequisites

The same as the 14-qubit build (see the top-level [README](README.md)): Vivado with the Zynq
UltraScale+ PS, RF Data Converter and SmartConnect IP, `mill` for RTL generation, and a machine with
at least 32 GB of RAM.

### Run

From anywhere in the repo:

```bash
vivado-scripts/riscvsoc-bd/build-riscvsoc-bd.sh \
    RISCQ_CONFIG=software/configs/zcu216-16q-430.json \
    RISCQ_PROJ_NAME=zcu216-16q-430 \
    RISCQ_SPAN=5 \
    2>&1 | tee build/zcu216-16q-430/build.out
```

`RISCQ_*=value` arguments are exported like environment variables. `RISCQ_SPAN=5` is required: the
default 3-per-row floorplan has room for only 15 cores.

The script then:

1. generates the block-design RTL into `build/zcu216-16q-430/` with
   `mill runMain riscq.soc.GenPulseTableSocJson <config> build/zcu216-16q-430 vivado` (a few minutes;
   skip it with `RISCQ_SKIP_GEN=1` when the RTL is already there — the RTL does not depend on
   `dsp_freq_hz`, so a folder generated for another frequency of the same config can be reused);
2. builds the block design, packaging `PulseTableSoc` as an IP next to the Zynq PS, the RF Data
   Converter and a SmartConnect, and configures the converters for 430 MHz;
3. runs synthesis, implementation with the span floorplan, the bitstream and the XSA export.

### Check the result

The script prints the post-route WNS/TNS when it finishes. A good build shows:

- `[rfdc-config] dspClk 430.0 MHz → DAC 6.880 GS/s (tile-2 PLL), ADC 1.720 GS/s` early in the log;
- "All user specified timing constraints are met" in `timing_impl.rpt`, and a `TOTAL 0` line in
  `cones_impl.rpt`;
- `PulseTableSoc.bit` and `PulseTableSoc.xsa` in the build folder.

These critical warnings are expected and also appear in every earlier build: `BD 41-1348` (the RF
Data Converter's AXI-Lite reset), `IP_Flow 19-4751` ×3 (missing `FREQ_HZ` on the IP's output clock
interfaces). A `CRITICAL WARNING: [rfdc-config] ... the CLK104 cannot supply` means the config asks
for a frequency this board cannot clock; do not use that bitstream.

### If timing misses by a little

Run the incremental `TimingClosure` pass on the finished build:

```bash
vivado-scripts/riscvsoc-bd/close-incremental.sh RISCQ_PROJ_NAME=zcu216-16q-430 RISCQ_SPAN=5
```

Use the same `RISCQ_PROJ_NAME` and floorplan setting as the build. It writes `timing_incr.rpt` and
`routed_incr.dcp` but no new bitstream; write one from `routed_incr.dcp` if the pass closes timing.
At 475 MHz it gained 23 ps (−0.078 → −0.055 ns).

### Building at another frequency

Copy the config, change `dsp_freq_hz` and `name`, and build as above. Pick a frequency the board
can clock: at most 430 MHz (or 500 MHz with the stock setup), and one the LMK04828 can make. Check
the second with:

```bash
cd software && python -c "from riscq.board.clk104 import plan; print(plan(425))"
```

`plan` raises `ValueError` for frequencies the chip cannot make.

## Running on the board

Upload the XSA together with the build's config as a bundle and load it (board server setup:
[software README](software/README.md#board-server)):

```python
from riscq.driver.remote import RemoteDriver, upload_bundle

drv = RemoteDriver("<board>", 9091)
upload_bundle(drv, "zcu216-16q-430",
              xsa="build/zcu216-16q-430/PulseTableSoc.xsa",
              params_json="software/configs/zcu216-16q-430.json")
info = drv.board.load("zcu216-16q-430")
assert info["mts_result"] == 0, "multi-tile sync missed its target latencies"
```

- **Clock chips.** `load()` programs the LMK04828 for the bundle's `dsp_freq_hz`. If `xrfclk` has no
  register file for 430 MHz, the driver supplies the one derived by `clk104.py`. `xrfclk` must be
  importable by the board server; on a PYNQ image it lives in PYNQ's Python environment. A
  `board.json` `lmk_freq` overrides the frequency.
- **Multi-tile sync.** Check `mts_result == 0` on the first load at 430 MHz: it is the first sign the
  derived clock settings work.
- **Nyquist zones.** At 6.88 GS/s the DAC's second Nyquist zone is 3.44–6.88 GHz (4–8 GHz at
  8 GS/s). Drive or readout tones above about 6.9 GHz need the third zone or external mixing.
- **Time base.** One `dspClk` cycle is 2.326 ns. Code that converts between cycles and seconds must
  use the build's `m.params.dsp_freq_hz`, as `riscq.cal` does, never a hard-coded 2 ns.

## Timing results

All 16-qubit builds of `PulseTableSoc` in the block-design flow, `dspClk` setup:

| Build | Period | WNS | Failing endpoints | Board can clock it |
|---|---|---|---|---|
| 500 MHz, 4 cores per row | 2.000 ns | −0.210 | 18,438 | yes |
| 500 MHz, span=5 | 2.000 ns | −0.216 | 8,657 | yes |
| 500 MHz, span=5, + incremental | 2.000 ns | −0.190 | 8,465 | yes |
| 500 MHz, span=5, current RTL | 2.000 ns | −0.211 | 8,600 | yes |
| 475 MHz, + incremental | 2.105 ns | −0.055 | 758 | no |
| 450 MHz | 2.222 ns | +0.031 | 0 | no |
| **430 MHz** | **2.326 ns** | **+0.016** | **0** | **yes** |

The 500 MHz rows before "current RTL" predate the two RTL fixes above.

### Why 500 MHz does not close

The failure is spread across the whole design rather than concentrated in one module. In the
current-RTL 500 MHz build, all 16 cores fail by 0.155–0.211 ns, routing is 72 % of the delay on the
40 worst paths, and the failing endpoints divide roughly evenly between the core pipelines, the core
↔ RF boundary and the RF channel buffers. The RTL fixes removed their target paths, but the next
paths behind them are also about 0.2 ns short. The cause is density: 16 cores in the X0 column and
16 qubits' channel logic in the X1–X5 datapath region. For comparison, 8 cores close at +0.037 ns and
14 cores at 0.000 ns (after the incremental pass) at 500 MHz.

Reaching 500 MHz with 16 cores would need structural work: more room for the cores than the X0
column, extra pipeline stages in the core's operand → address and branch-target paths, or a
pre-decoded command → buffer write path. None of these has been tried.

## Troubleshooting

- **Vivado aborts with `realloc(): invalid pointer` in `libudev` during the license check.** Some
  machines need system libraries preloaded before Vivado starts; login shells often set this in
  `~/.profile`. Run the build from such a shell, or prefix the command with the same `LD_PRELOAD`.
- **`no routed checkpoint` from `close-incremental.sh`.** It looks in `build/riscvsoc-bd` unless
  `RISCQ_PROJ_NAME` names the build folder.
- **`riscq_slice_band: no SLICE sites in X0Y8`.** The build ran without `RISCQ_SPAN=5`: the 3-per-row
  floorplan puts core 15 in row Y8, which this device does not have (its clock regions stop at Y7).
